## (d) HEADER_CAP survivor
Reproduced. t2-hdr: upload_stream.py `_check_header_size` -> `if False:`; `test_a_huge_part_header_is_refused_before_it_is_buffered` stays green, and the whole test_ui_intake.py is 20 passed. My own measurement (scratchpad/t2-d/measure.py, run on the mutant copy) shows why: one 40 KiB header, one 20 MiB header and 7000 distinct 8000-byte headers are all refused 400 "could not be read as a form" with peak memory under 0.1 MiB.
Cause: python-multipart 0.0.32 (pinned `>=0.0.32`, pyproject.toml:29) `MultipartParser(...)` at upload_stream.py:179 is built with its defaults `max_header_size=4224` (per header) and `max_header_count=8` (per part), raising `MultipartParseError("Maximum header size exceeded")`, which the code maps to 400 (upload_stream.py `except MultipartParseError`). HEADER_CAP = 8 KiB (line 33) is larger than 4224, so it can never fire first: dead code, not just redundant. The 40 KiB test proves the library's refusal. The builder's reason ("only the memory bound differs") is wrong in degree: with the library cap there is no memory difference at all.
Ruling: the header cap belongs to the streaming/bounded-memory intent of TI9/HO30 ("memory does not grow with the file"). That intent is met for headers by the library's own cap, so HEADER_CAP is unevidenced dead code; the correct control is one cap with a test that pins it (or an explicit parser argument). Two risks: the guarantee depends on a library default (a dependency that lowers the pin or changes the default silently removes it) and nothing in this repo asserts it.
Max bytes a hostile client can make the server buffer before refusal (measured with scratchpad/t2-d/measure.py, limit 64 MiB, 4 KiB-ish per figure below):
- one part header: 4224 bytes (library) / 8192 (upload_stream.py:33, :111-113, never reached); up to 8 headers per part, so at most ~34 KB held in `_head` (:116).
- one non-file field value: FIELD_CAP 16 KiB (:32, :146-147) plus one chunk before the check fires (`_buffer += piece` at :145 precedes the test).
- AGGREGATE of fields: unbounded count. `self.fields[self._name] = ...` (:154) keeps every distinct field name. Measured: 4000 distinct fields of 16000 bytes at a 64 MiB limit -> accepted `OK`, peak 61.6 MiB (vs 0.02 MiB for one field). The only bound is the whole-body check `total > limit + FORM_OVERHEAD` (:184), so on production (2 GiB default, 64 GiB ceiling) a hostile client can force about limit + 256 KiB of RAM through form fields before refusal (no cap on part count, no cap on `fields` size). FORM_OVERHEAD (:30) bounds the excess over the limit, not the non-file bytes; the docstring "what was read never exceeds the limit plus one chunk plus the form overhead" is true, the implied bounded memory is not. HO30 text only says "memory does not grow with the file", so the criterion as written is met; the hostile-form memory growth is a new finding, not covered by any test.
- preamble: a body that does not start with `--boundary` is refused by the parser (`Expected boundary character 45`), nothing buffered. boundary line: <= 256 bytes (library MAX_BOUNDARY_LENGTH).
- file part: never buffered, one chunk at a time to disk; written bytes <= limit (:139-140), read <= limit + FORM_OVERHEAD.
