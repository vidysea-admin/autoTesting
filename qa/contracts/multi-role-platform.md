## P0 leak banner and leak-evidence policy (from the intent file; binds every unit)

A data leak or privilege escalation is HIGHLIGHTED: always P0, release-blocking, in a banner at the top of the report, with reproducible
steps. The evidence is counts, field names, HMAC ids and masked screenshots, never third-party personal data (MPI1). Masking the data never
softens the finding.

## Invariants

- **MPI1 — Leak evidence stores no third-party personal data (A, intent "Safety").** A leak is recorded as: a count of foreign rows, field names (headers, not values), at most 5 ids hashed with HMAC-SHA256 under a per-project key from the repo-root `.env`, a screenshot masked before it is written, and the URL template with ids replaced by placeholders. Names, emails, phone numbers, marks and timestamps of another tenant's people are never written to disk, a log or a prompt. Leaked content never goes to a model: leak and privilege oracles are deterministic, a page an oracle flagged is excluded from the judge's evidence and from UX passes. Checked by MP9. Loosening this is a CRITICAL amendment.
- **MPI2 — Fixtures stay blind (A1).** Unit-test fixtures are synthetic and cover each rule class as a matrix. None may reproduce one benchmark finding's case; /checker rejects a fixture that does.
- **MPI3 — One enums file, one editor (A2).** `schema/multi_role_enums.py` holds every G11 enum (LinkKind, AccountOrigin, Priority, FindingClass, AssertChannel, Expectation, OracleName) and is created and edited by T-207 only. A later unit that needs a new enum defines it in its own schema file. Verify (any G11 unit after T-207): `git diff --name-only <base>..<candidate>` does not list it. `schema/enums.py` (300-line cap) is not touched.
- **MPI4 — Probes are bounded; writes follow the account.** Per run: at most 3 id-swap reads per endpoint, 1 list page per list view, one escalation attempt per role-assign control, a request-rate cap per platform, a wall-clock budget inside the `RunApproval` bounds. Writes follow `ALLOW_WRITES` as far as the supplied account permits (D-018, D-053, not re-litigated here). Two fixed lines: a real-money charge is never completed, and an escalation probe that succeeds is reverted in the same run with the revert recorded.
- **MPI5 — Credentials are keys only, scoped per platform.** Values live only in the repo-root `.env`; a RoleAccount names keys. `browser/secrets.py::_host_matches` is a suffix match, so a role account on a subdomain declares `include_subdomains=False` when sibling platforms share the parent domain (MP5). Mailbox access is read-only (MP16).
- **MPI6 — CEO-benchmark scoring rule (intent "Scoring").** The 69 findings are split into atomic findings before the G11 run; the list stays private under `.work/` and committed artifacts carry only counts and its sha256. Matching is one-to-one by the existing `acceptance_comparison`/`bench` scorer, never a second scorer. Unmatched AutoTester findings are "unadjudicated", neither TP nor FP, until Umesh rules. Ordering and independence follow the T-136 gate: the list's hash and commit time are recorded before the run; no scenario, fixture or prompt is written from a specific finding; a scenario derived from one is labelled and its matches excluded from recall. The scorecard prints one recall line per CEO technique naming its owning unit (multi-role comparison T-211/T-215, copy/branding T-216, inbox T-212, state-after T-220, cross-role consistency T-215, negative input T-219, handoff chain T-210/T-211, notification absence T-211/T-212, cross-tenant T-213, API error T-214, answer key T-215, responsive T-216, payment T-217, request count T-214); a technique whose owner did not run reads `not run`, never 0. Reported: recall overall and per priority (P0 first), recall excluding findings needing seeded data AutoTester was not given, FP rate over adjudicated findings, wall time (`unknown` until Umesh gives the CEO's active hours). Checked by MP29-MP31, MP35.

## Out of scope / ignore

Phone, SMS and WhatsApp channels; joining a live video meeting; completing a real payment; anything the supplied account may not do outside an escalation probe; storing or sending to a model any third-party personal data found by a probe; product-specific code (no PathLynks role, URL or label hard-coded); re-deciding write policy (D-018, D-053) or the T-136 ordering rule; the doc registration of O16-O21 in `docs/intent.md` / `docs/spec.md` / `docs/plan.md` / ARCHITECTURE rows (needs an authorizing D-entry, not a build gate for src units, see the 2026-10-18 amendment).
