## Acceptance criteria (verbatim) and evidence

- **TB1 — The bug key is stable.** `bug_key = content_id(project, case_id, failing criterion id)` for a case failure, and the `Issue.id` fingerprint for a video-found issue. It never includes a run id, a time, a path, or a screenshot hash. Three runs failing the same criterion are one bug; two failing criteria on one case are two bugs; a secret value planted in the case text does not appear in the key.
  Evidence: `test_tb1_*` (3 runs -> 1 bug count 3; 2 criteria -> 2 bugs; key depends on project/case/criterion only; planted `hunter2` absent). Falsification: clock hashed into the key -> `test_tb1_three_nightly...` RED.
- **TB2 — The lifecycle is a table, tested over every cell.** (none,FAIL)->open · (open,FAIL)->open count+1 last_seen updated · (open,PASS x k)->open k<N · (open,PASS x N)->fixed · (fixed,FAIL)->reopened · (any, INCONCLUSIVE|BLOCKED|NOT_RUN)->unchanged. N = 2 consecutive passing verdicts, a stored configuration value with that default.
  Evidence: `test_tb2_every_cell_of_the_table` (parametrised over every state x signal, 14 cells incl. stale), `test_tb2_the_table_is_total...`, streak-reset test, INCONCLUSIVE/BLOCKED test, reopen test, project-stored N test. Falsifications: INCONCLUSIVE counted as pass -> RED; N=1 -> 2 tests RED; FAIL no longer resets streak -> RED.
- **TB3 — Verdicts only, replayed runs included.** The loop reads `Verdict` and never `RawResult`. A replayed run (D-072) carries a judge verdict and counts like any other. A result with no verdict changes nothing. A PASS counts toward closing only when its verdict cites evidence.
  Evidence: `test_tb3_*` in the contract's order: RawResult-only run -> no bug; replayed run with verdict (RawResult.used_script=True) -> counted, closes; PASS with met=0 or screenshots unseen -> not counted. Falsifications: raw result's `assertion_failed` read as FAIL -> RED; unevidenced PASS counted -> RED.
- **TB4 — An honest close.** A `fixed` bug lists the run ids and verdict ids that closed it. If its case was deleted or its criterion changed, it becomes `stale`, never `fixed`. Closing a bug never deletes its pinned regression case.
  Evidence: `test_tb4_*` (two id lists read back; deleted case -> stale; rewritten criterion -> stale even after 2 PASSes; pinned case survives close and `delete_case` still raises `PinnedCaseError`). Falsifications: stale sweep disabled -> 2 RED; closing run ids dropped -> RED; close deletes the case -> RED.
- **TB5 — The adapter lives in `stages/issues.py`, in place.** Conversion `Issue -> TrackedBug` edited into the existing file, at most 58 added lines, the only place a key is derived from an `Issue`, file at or under 300 lines.
  Evidence: `git diff --numstat` = `16 0 src/autotester/stages/issues.py`; file is 258 lines; `autotester doctor`: clean; `test_tb5_a_video_found_issue...`. Falsification: key from issue.id + created_at -> RED. (`case_bug_key` is the case-failure key in `schema/tracked_bug.py`; there is one key function per source, none derives from an Issue outside issues.py.)
- **TB6 — Idempotent per run.** Processing run R twice yields the same bug set, counts and lifecycle states (a processed-run marker, portable file operations). A crash between two bugs of one run converges on retry with no double count.

## Assumptions and notes for the checker

- [ASSUMPTION] A `Verdict` has no evidence field on PASS. "A PASS cites evidence" is implemented as `criteria_total > 0`, `criteria_met == criteria_total` and `not graded_on_partial_evidence`. If the contract means another signal, that is one function (`signal_of`).
- D-074 (a failed assertion never PASSes) is the judge's rule, owned elsewhere; the loop trusts verdicts and does not read the RawResult.
- Verdict id = `<run_id>/<case_id>` (`verdict_ref`), the verdict's file location, since `Verdict` has no id field.
- `(stale, FAIL) -> open` (count reset) and `(reopened, FAIL) -> reopened` are my cell choices where the contract is silent; `fixed` bugs are not swept to stale (their closure record stays honest).
- A FAIL verdict moves only the bugs of its failed criteria; a PASS moves every open/reopened bug of that case.
- `BugStatus` lives in `schema/tracked_bug.py` because `schema/enums.py` is at the 300-line cap; persistence is module-level in `bug_loop.py` because `store/project_store.py` is at 300.
- Not handled: two concurrent `process_run` calls on one project (the run queue serialises per project, D-072 item 6).
- A case pinned from an issue (`pinned_issue_id`) does not yet map its failure to the video bug of that issue; separate keys today.
