## Judgement calls for the checker
1. **Two files beyond OG-AUTHZ (`schema/authz_probe.py`, `stages/authz_probe.py`).** OG-AUTHZ names only the two oracle modules, but the plan, the transports and the log are domain shapes that CLAUDE.md puts in `schema/`, and the approval/ceiling/budget/refusal path is shared by both oracles; writing it twice would be a doctor `duplicate-concept` and a second probe concept (A5). The names collide with no other group's list (checked against the wave plan ownership table).
2. **Approval kind is ADVERSARIAL, target = the platform's exact `base_url`.** Replaying another role's requests is adversarial by nature and ADVERSARIAL is never account-derived (`core/consent.py::ACCOUNT_KINDS`), so a human-granted row is needed; D-088 production handling comes free from `require_project_approval`. `planned` is an upper bound: tenant = 1 + owner list + 3 swaps; privilege = reads + 2 per control (the attempt and its possible revert); the gate covers the WHOLE plan whichever oracle runs. `PROBE_CEILING = 60` is the build's proposal (as `adversarial.PROBE_CEILING = 50` was); the owner confirms the number.
3. **How the oracle gets its inputs.** `run(context)` reads `<run_dir>/authz_plan.json` (an `AuthzPlan`), loads the project from `ProjectStore(slug)` (root = `repo_root()` / `AUTOTESTER_ROOT`), and needs `context.port` to ALSO satisfy `ReadTransport` (and `EscalationTransport` for MP19 writes). A missing plan, or a port that cannot read, raises (`AuthzPlanMissing`, `NoProbeTransport`) so the registry reports `errored` with the type only, never a silent empty pass. Nothing authors the plan file yet (no UI/CLI): that is later work.
4. **Foreign-row detection.** Owner mode: tenant A's list rows whose id is in the owner tenant's own list (the owner reads the same `list_url`, one page each). Count mode: rows beyond `declared_own_count`; nothing says WHICH rows are foreign, so their id field is dropped and the evidence is the count and headers only. Id swaps use the owner's ids (in memory, never in the plan or on disk), at most 3 per detail endpoint, and a 2xx with a row counts; a row seen both in the list and by swap counts once.
5. **What a "success" is.** Privilege: the lower role's replayed read answers 2xx (`ProbeReply.ok`); the transport must report the final status after redirects, a login redirect as 401/403 (stated in `ProbeReply`'s docstring). Role-assign: `EscalationTransport.assign` returns True.
6. **Revert.** Reserved up front (`take(reserve=2)`), so the cap can never starve the undo; recorded in `<run_dir>/authz/reverts.jsonl` and said in the finding title ("reverted in run" / "NOT reverted, undo by hand"). An assign that raises gets a best-effort revert, no finding, and (cycle 1) a `RevertRecord` saying whether the undo held.
7. **Write policy.** A role-assign is a write, so it is attempted only at `ALLOW_WRITES` (D-018, D-053, not re-litigated); below that the controls are listed unprobed with reason `write_policy`. Reads are not gated by it.
8. **Cap and wall clock span both oracles on a platform** through `authz/<oracle>_log.json` (`prior_usage`), so tenant + privilege together cannot pass `request_cap`.
9. **CORE-REQUEST: T-210 multi-role session port** must implement `ReadTransport.read(role_id, url)` (and `EscalationTransport` for MP19 writes) in addition to `RoleSessionPort`, since `OracleContext.port` is typed `RoleSessionPort` only.
