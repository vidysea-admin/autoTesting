## Judgement calls the checker should look at

1. **Generated login keys are always write-only on the table.** `env_table` never prefills `<NS>USER_EMAIL` / `<NS>USER_PASSWORD`, even for a `credentials.view` holder (with auth off in tests `can_view_credentials()` is True). Without this the E3.5 canary falsifier fails. It is a narrowing of "table exactly as today" for these two keys only (`role_accounts_view.py:203`, mutant m8).
2. **`redisplayable_key` vs AT-068.** AT-068 (`test_a_rejected_key_is_never_echoed_back`) forbids echoing a rejected key because someone may paste a secret into the key box. E3.1 wants the typed key kept. Resolution: only name-shaped input (`[A-Za-z][A-Za-z _-]{0,63}`) is redisplayed; anything else, including values that look like tokens or contain digits and punctuation, is blanked. AT-068 passes unchanged. Please confirm the rule is the right line.
3. **The login block posts to the existing `/projects/{slug}/env/add`** with a hidden `block=login`, so no new route was needed (route policy table, pinned policy test and golden `ui_routes.json` untouched).
4. **The view functions live in `role_accounts_view.py`**, not a new module, and `env_editor_view` stays in `routes_credentials.py`, which keeps the state-bypass baseline rows (keyed by function name) valid.
5. **`stages/role_onboarding.py` was touched** only to add the single key-pair helper.
6. **Onboarding refusals are inline** (status 400 with the full form redisplayed). A foreign scope or half a login on `/onboard` saves nothing.
7. **The email field is `mask_in_screenshot=True` too.** The contract requires it only on the password; masking both is the more private reading.
8. **E3.6 is verified at markup level only.** I did not take a browser screenshot at 500px; the checker takes it.
9. The earlier pass at this file had a stale `docs/MAP.md`; it is regenerated and committed here.
