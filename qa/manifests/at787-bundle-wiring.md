## Criteria (verbatim from the brief)

- **W1.** When a case run ends in FAIL or ERRORED on the production pipeline path (`run_and_grade_case` and its resilient variant), a failure bundle is built and written under the project's bundles dir. Passing and INCONCLUSIVE runs build none.
- **W2.** The failing step is taken from the run's real step results, not the heuristic default, whenever the result carries one.
- **W3.** If bundle building raises, the case verdict is unchanged. The error is logged through the Redactor, and the run still completes.
- **W4.** No raw secret or unmasked screenshot ends up in a bundle written from the pipeline. Reuse the existing gates.

## Design notes the checker should weigh

- **ERRORED counts as a failure even though its verdict is INCONCLUSIVE.** `grade._outcome_verdict` returns INCONCLUSIVE by rule for an ERRORED execution, so "FAIL or ERRORED" is implemented as `verdict.result is FAIL or result.outcome is ERRORED`. "INCONCLUSIVE builds none" is read as an INCONCLUSIVE whose execution did not error (an unjudged replay, a grader crash after a COMPLETED run, a judge INCONCLUSIVE). BLOCKED_HITL and NOT_RUN also build none.
- **"Real step results"**: `RawResult` has no step-result list; the recorded signals are its evidence and error. `recorded_failing_step` uses, in order: the first step with `assert ...: unmet` evidence; the step named by `step N (` in an ERRORED error; the first step of an ERRORED run with no post-step screenshot. It returns None when the result records none, and only then does the old max-screenshot heuristic apply.
- Trace slice is `read_spans(store.paths.run_trace(run_id))` (empty when no trace was written). Screenshot sources are resolved against `session.state.run_dir`.
- Process note: the implementation was written before the driver tests; red evidence comes from the sabotage table below (same as the T-178 verdict's PROPOSED-ISSUE 3).
- Not done: no ARCHITECTURE.md concept-map row (needs a DECISIONS entry); `docs/SNAPSHOT.md` is stale (see doctor output).
