## 1. Stalled holder: the fencing epoch

Z is a holder that stalls (GC pause, partition) past its 30 s lease at some point inside a write; S is whoever takes the lease next and commits.

**Mechanism** (`auth/store_mongo_tx.py`, 300 lines, no new src module):
- **Epoch.** `auth_meta/epoch` is a counter bumped by compare-and-set at every `lease()` acquire (`_next_epoch`), so each holder has an epoch no earlier holder had. `Lease(meta, owner, epoch)`.
- **Journal per epoch.** Marker `auth_meta/tx:<epoch>` (`state` open / aborted / committed); entries `auth_users/undo:<epoch>.<seq>` (still in `auth_users` so `$argon2` stays there only, M30). An entry records `op` (`ins` / `set`), `coll`, `doc_id`, `me` (its own stamp), `pre` (the stamp it read), `prior` and `gone`. It carries NO document body (hashes stay out of the journal, M30).
- **Stamped writes.** Every data document carries `_e`. A holder's write is conditional on the stamp it READ: `update_one({_id, _e: pre}, {$set: {..., _e: new}})` (a delete is the same update with a `G:` stamp); a miss raises `AuthStoreBusy("the document changed under this writer")`. Inserts rely on the unique `_id`.
- **Write order (`_log`)**: C1 `_alive()` (lease still mine, and once I have a marker it is still open and mine) -> insert marker (lazily) -> insert entry -> C2 `_alive()` -> caller writes. The entry is therefore durable before the write, and the lease was re-checked AFTER the entry and before the write.
- **Recovery (`recover` at every acquire)**: for every epoch other than its own, found from `kind:tx` markers AND `kind:undo` entries (so a straggler entry with no marker is found too), `_resolve`: (a) CAS the marker open -> aborted (this alone stops Z from ever committing, because `commit` is a CAS open -> committed), (b) re-read it; if committed only sweep the entries (and make a journalled delete physical, below), (c) otherwise replay newest first, deleting each entry after its replay.
- **Every replay write is a compare-and-set on the stamp (cycle 1, B1 and B2).** `_replay(store, entry, by)`: a dead holder's entry (`by` = the recovering epoch) is first FENCED (a `set` re-stamps `pre` -> `F:<pre>`; an `ins` inserts a tombstone), then undone only where the document still carries a stamp of that write: `mine = {me, G:me, F:me}`. The undo stamps `F:<pre>`, whoever performs it, so the next older entry on the same document (`me_{k-1} == pre_k`) matches `F:me` and a second recoverer picks up exactly where a killed first one stopped (B1). A stale or repeated replay finds the stamp moved on and writes nothing. A holder's own rollback restores `pre` exactly.
- **A delete is a journalled update, not a delete (cycle 1, B2).** `_drop` writes `_e = G:<stamp>` (conditional on the stamp read) with `gone: true` in its entry; `hidden(doc)` makes every read treat a `G:` document as absent. At commit `_resolve(..., None)` removes the entries and physically deletes the `G:<me>` documents. Recovery of an aborted journal restores `pre` by CAS. Nothing is ever re-inserted unconditionally, so a late replay can never resurrect an account a later holder deleted.
- **Tombstones** are invisible (`HIDDEN`) and carry a placeholder for every unique index (`email`, `generation`, `name` = `fence:<coll>:<id>`, A3/B4: a missing field is null and null is ONE value on a real unique index). `_insert` clears a tombstone when its `f <= held.epoch` (the holder's own epoch included, so a recoverer may make the same insert itself); a stalled earlier epoch hits it and gets `AuthStoreBusy`.

**Closure argument (why every interleaving is covered).** Z's data write D comes after Z's entry E, and after C2 (which passed). Cases by when S acquired:
1. S acquired before C2 evaluated: S holds (or held) the lease, so `held()` is false -> D is never attempted.
2. S acquired after C2 passed: E is in the database (it was inserted before C2) so S's scan finds it (via marker or via the entry), fences the document (D now fails its stamp condition) or, for an insert, leaves a tombstone (D hits it). D cannot land.
3. S acquired between Z's C1 and Z's entry insert (the entry does not exist when S scans): C2 runs after the entry insert, S already holds or has released the lease, so `held()` is false -> D is never attempted; E is a straggler, found by the next acquirer through the `kind:undo` scan (test `before-its-entry`).
4. Z tries to commit while S replays: S aborted the marker first, so Z's commit CAS fails (test `..._cannot_commit_while_its_journal_is_being_undone`).
5. S dies part way: its own marker/entries are an epoch like any other and the next acquirer resolves them; the fences S already wrote stay (they are stamps / tombstones from an earlier epoch, removable by any later one).

Z's `_alive()` marker check is belt and braces: `held()` alone already covers cases 1-3 (so a mutant that drops the marker check is an equivalent mutant, not listed).

**Residual, stated honestly.** (a) A tombstone on a DETERMINISTIC id (a grant `slug|user|relation`) is cleared by the same or a later epoch, so the first legitimate writer after a fence re-creates it (tested both ways). (d) NEW LIMITATION: deleting a document and re-inserting the SAME id (or unique key) inside one transaction is not supported; it raises a loud duplicate, never silent corruption. `replace_project_owner` was the one caller that did this and was rewritten (`store_mongo.py`: drop the other owners with a `user_id $ne` filter, then `add_project_relation`). (b) A reader never recovers a straggler entry that has no marker; it is harmless to readers (hidden) and swept by the next writer. (c) A-W3 (writers wait up to 30 s behind a stalled holder) and the U9 `_CACHE` race are NOT touched (flagged below).

## 2. Reader window
`MongoAuthStore.reading()` calls `dead_marker(store)`: True if there is a `kind:tx` marker with `state != committed` whose owner does not hold a live lease (lease missing, expired, or another owner). Then it takes the lease once (which runs the same recovery) before reading. A reader that finds a LIVE holder's marker does nothing (that is the unchanged live-holder read, a write may be visible just before its rollback; every rollback follows a refused change, which only lowers privilege - the existing docstring). Cost: +1 `find` on `auth_meta` per read.
Test: kills the store at every call point (1..) of the refused `update_group` that grants `users.manage` to the developer group, ages the lease, and the FIRST store contact is `sessions.resolve_session(token)` for a signed-in developer: it must never carry `users.manage`. Non-vacuous: the test asserts the raw document had `users.manage` at >= 3 kill points. Every other kill point also runs a second death inside the successor's recovery (marker `aborted`), which is what made `dead_marker` use `state != committed`.

## 3. Rehash parity
`accounts.authenticate` -> `needs_rehash` -> `tx.set_password_hash` (accounts.py:126-128). The Mongo `set_password_hash` used to call `delete_user_sessions` first, SQLite did not (`store_sqlite.py:79-81`). Now both stores just write the hash. The revoke-first ordering lives where the intent is: `accounts.reset_password` (`change(tx)`: `delete_user_sessions` then `set_password_hash`) and `accounts.bootstrap_admin` (`delete_user_sessions` then `enable_with_password_hash`). Behaviour change on Mongo only: a login-time rehash no longer ends the user's other sessions (it now matches SQLite). Parity test is parametrized over both backends.

## 4. Sweep leftovers
Committed entries are swept by `_resolve` for ANY epoch that is not the caller's; `committed` is read from the marker so a committed journal is never replayed. Test: delete_one on `undo:` ids is made to fail (`AutoReconnect`) during `reset_password` / `delete_user`, which leaves entries holding the old password hash / the deleted account's document (asserted present); the next writer sweeps them, no `undo:` doc remains, the committed change stands (new password works, old does not; account stays deleted), and for delete no copy of the account's email remains in `auth_users`.
Behaviour note: while a sweep keeps failing, the NEXT acquire's recovery also raises (the store is unreachable for deletes); it does not skip a failed sweep, which would hide the leftover.

## 5. Stronger recovery assertion
`_refused` in `tests/test_auth_store_recovery.py` now, after the store dies at call k and the lease is aged, FIRST asserts read-only that the shape is unchanged, an enabled admin remains, and a signed-in developer's session does not resolve to `users.manage`; only then runs the refused `claim_admin` and re-checks the shape. So "the write is gone" is asserted BEFORE the next holder takes the lease (readers now recover), not only after.

## Cost (extra database calls)
- per acquire: epoch bump (1 find + 1 update, first time 1 insert) and a recovery scan (2 finds: markers, entries) instead of one marker find.
- per write: C1 + C2 are 1 find each before the marker exists, 2 each after; the conditional write itself is the same one call. First write of a transaction also inserts the marker. Net about +3 finds per write.
- per commit: marker CAS + one delete per entry + marker delete.
- per read: +1 `find` on `auth_meta`.
All writes were already serialised behind a lease; no new lock.
