## Findings

1. **File-mode equivalence holds, byte for byte (store unset).** One workload (`probe_b/test_diff.py`) ran against master `4df612ca` (extracted with `git archive`; `autotester.__file__` confirmed to resolve to the extracted tree) and against the branch: role onboarding with `#`, `$`, quotes and spaces in values, role-account edit, duplicate onboarding (400), `/onboard` intake, duplicate-key and server-key intake (400/403), `/projects/pl/env` save, `/env/add`, malformed value (400), the env page for admin/dev/tester, the accounts page, undeclare and undeclare of a missing key (404), then `SecretStore.load` `_values`/`_shadow`/`undeclared`. Result: 20 of 20 outputs SAME (status, Location, normalised body, `.env` text after every step, `project.json`, SecretStore maps). The `.env` text was non-trivial (quoted values with `#`, `$`, `"`, a tab). Code read agrees: `core/env.py:259-278` with the store off returns exactly the old `usable`/`shadow` split, and `browser/secrets.py:149-153` `missing` is equivalent because `usable` holds every truthy declared key.
2. **Never both (M35).** `ui/env_editor.py:233-241` `save_credentials` returns after the store branch and calls `set_env_values` only when `credential_collection()` is `None`. Probe `test_P8_preexisting_env_untouched_in_store_mode`: with a pre-existing `.env`, role onboarding, intake, env save, env add and a role-account edit in store mode leave the `.env` bytes identical and the values only in `secrets` (6 docs, each with the right `p`). `routes_settings.py:105` still writes server keys to `.env` only (M36), correct.
3. **M37 snapshot/restore round-trips and survives a failing project restore.** `ui/routes_role_accounts.py:216-228`: snapshot before the first write, restore in a `finally` after `_restore`. Probes: `T4` (edit; `save_project` raises AND `_restore` raises) leaves `secrets` equal to the pre-edit documents including `updated_at`; `T4b` (new project, same double failure) leaves `secrets == []`; `T2` (one-shot store blip at the 3rd write of a new project) returns 503 with no docs, no project, no `.env`; `T2b` (blip at the 2nd write of an edit) restores the previous documents. The maker's bug-fix note (manifest item 9) is real and covered.
4. **Outage reads fail closed before any write (M26/M32).** `test_P7`: with the fake down, `/onboard`, `/onboard/roles`, `GET /projects/pl/env`, env save and env add all return 503; no project is created (`n1` absent), `pl` declares no new key, no value is in any collection, and the only file that changed under the data root is `.work/audit.jsonl` (an access-audit append that does not contain the planted value). The guard's store read (`_guard_intake` `ui/app.py:127`, `_env_now` `ui/routes_role_accounts.py:151-153`) is what stops the writes early.
5. **WARNING W1 - `undeclare_secret` is not atomic under an outage (M37 and the 503 text).** `ui/routes_project_edit.py:260-263` saves the project (declaration gone) and only then calls `drop_credentials`. Probe `T5`: store down during `POST /projects/pl/secrets/PL_PASS/delete` returns 503, the declaration is already removed and the `secrets` document remains; a second POST is a 404 ("no declared credential"), so no route can purge it; if the key is declared again the old value resolves. The themed 503 says nothing was changed, which is false here. No value leaks (it was stored already) and it needs an outage at that exact moment, so I do not read it as an M37 falsifier, but it breaks the fail-closed idea. Suggested fix: drop the document first (a failed drop leaves the declaration so the retry works), or put the declaration back on failure.
6. **WARNING W2 - a multi-key store write is not atomic.** `ui/env_editor.py:226-227` loops `_put_doc`. Probe `T1`: an outage at the 2nd of three keys leaves the 1st written (`['PL_A']`). The role-account commit compensates (finding 3), but only if the store is back for the restore: `T3` (outage persists through the restore) leaves partial new documents while `project.json` is restored; and `/onboard` intake (`ui/app.py:192-196`) saves the project and sources first and has no compensation at all. File mode is one atomic `.env` write, so this is a store-mode gap. It is a limit of any non-transactional store and the contract does not require atomic batches (M32 only forbids fallback and a partial return). Record it for U8/U12 and for a follow-up that adds a compensating path to intake.
7. **ADVISORY A1 - `drop_credentials` has no caller for role accounts or projects; I judge M37 met by the primitive, no owner needed now.** `grep -rn drop_credentials src` finds only `routes_project_edit.py:263`. No route removes a role account (`stages/role_onboarding.py:60-64` `merge_by_id` only adds or replaces; `routes_role_accounts.py:269` keeps every `SecretRef`) or a project (no delete route touches projects or accounts). So the M37 falsifier "after deleting the account a read still returns a value" has no reachable path today. `drop_credentials(slug, None)` also deletes `browser_sessions` (`env_editor.py:250-254`) and every delete carries `p` (`delete_many({"p": slug})`, `delete_one({"_id": key, "p": slug})`); the guard rejects an empty or unscoped filter (`store/mongo_guard.py:70-86,173-177`). The checker seat should fold into the contract that any future role-account or project deletion route must call it, and U12 owns the session writer.
8. **ADVISORY A2 - cached secret gate and per-write backend rebuild.** `_rearm` (`env_editor.py:201-205`) calls `reset_default_backend()` (`store/mongo_backend.py:295-296`), so each credential write, drop or restore builds a new `GuardedStore`/`MongoClient`, re-runs `ensure_indexes` (probe `T6`: 3 saves = 3 clients, about 130 server operations per save) and never closes the old client. Within one process the gate is rebuilt correctly and nothing holds a stale backend (`store/filestore.py:150-156` calls `default_backend()` each time). Under `--max-instances 1` that is the only writer; a writer in another process (the U8 `store migrate` CLI) will not refresh the running server's cached gate until the server restarts or does its own credential write. Not a criterion breach; U8 must note it.
9. **No U11 baseline row is stale.** `uv run autotester doctor` reports `doctor: clean`, and the stale rule (`ledger/committed_fresh.py:280-297`, `STATE_BYPASS_STALE`) fired nothing. The U11-tagged rows (`pyproject.toml:107-108,138-139,168-181`) all name functions that still read or restore the repo `.env`, the home of deployment secrets (M36). All touched files are at or under 300 lines (largest: `store/mongo_backend.py` 300, `browser/secrets.py` 299, `core/env.py` 298); doctor enforces function length and found none over 50.
10. **Other criteria spot-checked from this seat.** M36: `put_credentials` (`env_editor.py:221-224`) refuses the Mongo URI key and `is_server_key` keys (provider keys, `AUTOTESTER_*`) by name and writes nothing for the batch; intake with `AUTOTESTER_APPROVAL_KEY` returns 403 and stores nothing (`P9`). M31: `credential_collection(` appears only in `core/env.py` and `ui/env_editor.py`, there is one `replace_one` in the door and no `cryptography` import. M33: every consumer of `.env` credentials goes through `SecretStore.load`, which now resolves through `resolve_credentials`, so none was left on a file-only read. The guard's `find` returns a list (`store/mongo_guard.py:121-125`), so the double iteration in `resolve_credentials` is safe on the real driver.
